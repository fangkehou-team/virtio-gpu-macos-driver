## 3. 逆向:macOS 15 的合成器选择闸门(SkyLight/CoreDisplay)

SkyLight 里 `device_composite_windows(CGXDisplayDevice*, …)`(`__ZL24device_composite_windows…`):

```
edi = 0
if (dev && (dev->[0x64] & 0x10))            // 显示设备的“有加速器”标志
    edi = CGXGLDisplayDeviceAccelerator(dev)
compositor = WSGetCompositorForAccelerator(edi)
if (!compositor) -> 软件回退路径
```

- `_CGXDisplayDeviceHasAccelerator(dev)` = `dev && (dev->[0x64] & 0x10) && CGXGLDisplayDeviceAccelerator(dev) != 0`
  —— 与上面同一条闸门。
- `_CGXGLDisplayDeviceAccelerator(dev)`:
  - 若 `WSMetalCompositorEnabled()`:`CGXAcceleratorForDisplayDevice(dev, -1, &accel)`;
    `accel != 0` → 返回 `accel`(Metal 路径);否则落回 GL 路径。
  - `CGXAcceleratorForDisplayDevice` 在 CoreDisplay(`cd.dis`)是个**虚调用**
    `dev->vtable[0x148](dev, …)`。
- `_WSGetCompositorForAccelerator(accelId)`:`accelId != 0 && metal_lovin && active_compositor==0`
  → `WSGetCompositorMetal`,否则 `compositor_sw`。
- `_WSMetalCompositorEnabled()` = `active_compositor == 0 && WSSystemCanCompositeWithMetal()`
  (后者的 `once` 块算 `metal_lovin`)。
- `_CGXSetOpenGLAcceleration(dev, on)`(CoreDisplay)写 `dev->[0x10]->[0x133]`,并在
  `(dev->[0x64] & 0x100080) != 0x80` 时 `CGXIncrementDisplaySystemStateSeed()`。

即:合成器闸门 = **`displayDevice+0x64` 的加速器标志位** × **`CGXAcceleratorForDisplayDevice` 非 0**
× **`metal_lovin`**。实测这些在 macOS 15 上**都成立**(否则 §1/§2 不会有 GPU 合成输出)。

## 4. 与 AMD(Apple 内嵌驱动)的拓扑对比

Apple 内嵌:`/System/Library/Extensions/AMDRadeonX6000*.kext`(未加载,无 AMD 硬件)。

| | AMD(Navi10) | 本驱动 |
|---|---|---|
| IOFramebuffer | `AMDFramebuffer`(IOClass `AMDFramebuffer`,**IONameMatch `display`**,provider `AtiFbStub`) | `VirtIOFB`(provider `VirtIOGPU`,category `IOFramebuffer`,score 60000) |
| IOAccelerator | `AMDRadeonX6000_AMDNavi10GraphicsAccelerator`,**IOMatchCategory `IOAccelerator`**,provider `IOPCIDevice` | `VirtIOAccel`,同 category、同 provider |
| GL/Metal 驱动 | `AMDRadeonX6000GLDriver.bundle` / `…MTLDriver.bundle` | `VMTLDriver.bundle`(Metal);无 GL |
| 驱动包关联 | Info.plist 里**没有** `IOGLBundleName`/`MetalPluginName`,靠约定/运行时 | `MetalPluginName`/`MetalPluginClassName` 走 Info.plist |

本 guest 的实际 IORegistry(`ioreg -w0`)在 `S38@7`(IOPCIDevice,virtio 1af4)下:

```
S38@7
├── AppleVirtIOPCITransport
├── IONDRVFramebuffer            ← 固件/通用 framebuffer(matched/active,但无 display 子节点)
│   ├── AppleMCCSControlModule / AppleUpstreamUserClientDriver / AGPM
├── VirtIOGPU
│   ├── VirtIOFB                 ← 真正在用(category IOFramebuffer, score 60000)
│   │   ├── display0 → AppleDisplay
│   │   ├── IOFramebufferUserClient / IOFramebufferSharedUserClient   ← WindowServer 的 client
│   │   └── AppleMCCSControlModule / AppleUpstreamUserClientDriver
│   ├── IOAccelVirtIOGPUUserClient      ← (Info.plist 的 IOUserClientClass,见 commit 0a258d6)
│   └── VirtIOAccel
│       ├── IOAccelDevice2 / IOAccelSharedUserClient2   ← WindowServer 的 accel client
```

要点:
- `IONDRVFramebuffer` 也在同一 PCI 节点上 matched/active(通用类),但它**没有 `display0`**,
  真正的显示在 `VirtIOFB` 上;`IONDRVFramebuffer` 持有 `IOAccelTypes =
  "IOService:/…/S38@7/VirtIOAccel"`、`IOFBIntegrated = Yes`。它没抢走合成路径(§1/§2 为证),
  但字段面上和真实 AMD 的“单 framebuffer”拓扑不同,值得注意。
- `VirtIOAccel` 发布 `MetalPluginName`/`MetalPluginClassName`(见 `kexts/VirtIOGPU/Info.plist`),
  WS 据此实例化 `VMTLDevice`。
