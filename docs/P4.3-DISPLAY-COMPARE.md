# P4.3 — 显示栈对比：iOS（UniXNU）vs macOS（本驱动）

日期:2026-11-01;最后实测更新:2026-11-14。对照来源:`tmp/UniXNU/`(drivers/GopFramebuffer、
drivers/AdrenoMetal、docs/porting/{display,gpu}.md)与本仓库 kext/plugin。目的:定位"为什么 iOS
上的驱动能正常用、我们卡在哪",并据此把缺口落成可开发的清单。

> **状态提示:** §0–§7 保留了攻关过程中的历史分析,其中“transaction 是空壳/调用 0 次”等
> 描述已经过时。真实 display-pipe 呈现现已打通,并已通过持久 OpenCore 配置的新 QEMU
> 冷启动验收;最终实现、实测数据及剩余限制见 **§9**。

## 0. 一句话

**iOS 的显示驱动拥有"帧的交接";macOS 的 WindowServer 拥有"合成器的选择"。**

iOS 上 render server 永远走 Metal,display 驱动的职责只是把合成器交出来的帧搬上屏
(offer → GPU blit → complete)。macOS 上多了一道 **driver 无法关闭的选择闸门**
(`useIOP` 偏好 × `gpuVendors`),过了闸之后呈现路径还要求 display surface 能包成
一个 **Metal texture**。这道门是 macOS 独有的,UniXNU 既没解也没踩过。

## 1. 两套显示栈的结构

### iOS / UniXNU

```
SpringBoard / render server  (永远 Metal,无软件合成器)
      │  swap: 合成器的 IOSurface 页
      ▼
NativeLegacyDisplay / NativeMobileDisplay   (display 驱动, IOMobileFramebuffer 家族)
      │  native_legacy_gpu_offer(surface 页)          ← NativeLegacyDisplay.cpp:44
      ▼
NativeGOPPresenter  (display↔GPU 交接的 wire, IOService + IOUserClient)
      │  NGP_METHOD_WAIT_SWAP → 把 surface 页 map 进特权 client
      │  NGP_METHOD_COMPLETE_SWAP → 退休 swap
      ▼
GpuScanoutClient / GpuScanoutPresenter   (特权 GPU client, 用户态)
      │  newBufferWithBytesNoCopy(scanout) + newBufferWithBytesNoCopy(surface)
      │  blit / compute-kernel: surface 页 → 固件 scanout
      ▼
固件 GOP scanout 内存
```

关键:iOS 上 **display 与 accelerator 的关联是隐式的**——display 驱动直接拿到
accelerator 连接去拷贝。display 对 surface 的唯一要求是它的**物理页**
(`newBufferWithBytesNoCopy` 导入即可)。**不存在合成器选择闸门。**

### macOS / 本驱动

```
WindowServer
      │  ① 选择合成器: CoreDisplay::UseIOPPresentment() × GetSystemGPUVendors()
      │     → WSGetCompositorForAccelerator → CompositorMetal | CompositorSW
      │  ② 呈现: CDDisplay::present_update → Display::Present
      ▼
CoreDisplay::DisplaySurface
      │  GetMTLTexture(MetalDevice*)   ← 要求 surface 能包成 MTLTexture
      ▼
IOAccelVirtIOGPUUserClient / VirtIOAccel  (IOGraphicsAccelerator2 家族)
      │  VIOAccelDisplayPipe: initScanoutResource / performTransaction(空壳)
      ▼
VirtIOAppleParavirtFB (IOFramebuffer) → VirtIOGPU → virtio-gpu PCI → 宿主
```

关键:macOS 上 display↔accel 关联是 **显式的、由 CoreDisplay 掌握**:
`useIOP` 偏好 × `gpuVendors` 位图决定合成器;过了闸后 `DisplaySurface::GetMTLTexture`
要求 surface 有一个 Metal texture。

## 2. 差在哪 —— 逐层对照

| 层 | iOS (UniXNU) | macOS（我们） | 差异性质 |
|---|---|---|---|
| 合成器选择 | 无闸门,永远 Metal | `useIOP` × `gpuVendors` 闸门 | **macOS 独有,driver 不可控** |
| display↔accel 关联 | 隐式(display 拿 accel 连接) | 显式(CoreDisplay 依 display pipe + 属性解析) | macOS 需 driver 提供 pipe |
| 帧交接的拥有者 | **display 驱动**(offer/complete) | **WindowServer**(present_update) | 拓扑方向相反 |
| surface→显示 的路径 | display offer → GPU client blit → scanout | `Display::Present → GetMTLTexture → accel` | 我们对后者只有空壳 |
| display 需要 surface 给什么 | 只要**物理页** | 满足 CoreDisplay 的 **Metal texture** 接口 | 我们缺接口实现 |
| 抓帧/退休机制 | NGP swap slot + 序列号退休 | `IOAccelDisplayPipeTransaction2` + `isTransactionComplete` | 我们对 transaction 是空壳 |

## 3. 已验证的事实(2026-10-31 / 11-01)

- **vendor 位图补上了但不够**:把 fb 类名改成 `VirtIOAppleParavirtFB`(Info.plist IOClass +
  `OSDefineMetaClassAndStructors`)后,`gpuVendors` 从 0 变 **0x10**(AppleParavirt 位),
  mask 校验能过。代码在 `kexts/VirtIOGPU/VirtIOGPU.cpp`,未提交。
- **`useIOP` 是独立偏好,不是从 `gpuVendors` 推导**:`CoreDisplay::UseIOPPresentment()`
  先看 `useIOP`,只有它 ==1 才用 `gpuVendors` 做 mask 校验。`useIOP` 唯一写点是
  `CGXMappedDisplayStart`,从具名偏好键(`useIOP` / `useIOP_on*` / `enableWSAA_on*`)读,
  默认 0。实测 guest 上 `useIOP=0`、`useIOP_on*` 全 1。
- **硬开闸就崩**(实验 A,`tmp/run_bp41_root.sh`):`vioscanout=0` + poke `useIOP←1` →
  WS SIGABRT 在 `CoreDisplay::DisplaySurface::GetMTLTexture(MetalDevice*)` ←
  `AccessComplete` ← `Display::Present`。**即使过了闸,下一堵墙是"display surface 没有
  Metal texture"。** 无 `CompositorMetal` 命中。
- 早先 `bp34` 的 poke 成功(`vioscanout=1` + `useIOP←1` + `gpuVendors←0x10` → CompositorMetal)
  是带 presentment-object 的配置,不可推广;Metal-texture 缺失才是 P4.2(e) 的真实边界。
- 详参见内存 `vmtl-compositor-is-software`。

## 4. 结论:能补什么、不能补什么

**不能补(driver 边界之外):**

1. `useIOP` 闸门本身 —— 是 WindowServer 读的偏好,不是 driver 能 setProperty 的东西。
2. 闸门之上"合成器选 Metal 还是 SW"的决策 —— 全在 CoreDisplay/WindowServer。

**能补(本驱动职责内,且与 UniXNU 拓扑一一对应):**

3. **display pipe 的呈现路径** —— 目前 `VIOAccelDisplayPipe` 全是 probe 空壳
   (`VirtIOAccel.cpp:379-396`)。需要:
   - `initScanoutResource` 返回真正包住 scanout 的 `IOAccelVidMemory`
     (`vioAccelScanoutMemory` 已具备,`VirtIOAccel.cpp:632`);
   - `performTransaction` 真正做 surface→scanout 的拷贝(对应 UniXNU 的
     `GpuScanoutPresenter` blit),`isTransactionComplete` 真正按序列号退休
     (对应 UniXNU 的 `NGPComplete`);
   - `VIOAccelSurface::submitSwapCopy` / `copyFromBuffer` / `copyToBuffer` 从 `false`
     变成真实的表面拷贝(`VirtIOAccel.cpp:334-342`)。
4. **surface→Metal texture 接口** —— CoreDisplay 崩溃点要的那个 texture。插件侧已有
   雏形(`plugin/VMTLDevice.m:728` `newTextureWithDescriptor:iosurface:plane:`、
   `vmtl_surface_image_create` 的 IOSurface→VRAM 别名),但 CoreDisplay 要的入口未打通。

> 判断:**第 3 项就是 UniXNU 那半张蓝图的 macOS 对应物**——display pipe 持有 swap slot,
> GPU 把合成器的 surface 页搬进 scanout,再按事务退休。这是我们可以独立完成、且拓扑与
> UniXNU 一一对应的部分。

## 6. Apple 自家 x86 参照(2026-11-01,新)

本 guest 自带 Apple 自己的 **x86** 半虚拟化 GPU 驱动,正是我们伪装的那一族
(PCI `0xEEEE106B`、`IOFramebuffer` 家族、`IOAccelDisplayPipeCapabilities`)。从
`SystemKernelExtensions.kc` 里把 `AppleParavirtGPU` 镜像整段抠出(`tmp/paravirt/`,
符号表 1229 条,`tmp/pvdis.py` 按原始字节反汇编),得到的是**权威的 x86 实现**,比
NVAccel 更贴近我们要模拟的拓扑。关键发现:

- **`AppleParavirtDisplayMachine` 继承的是 `IOAccelDisplayMachine`(基类),不是
  `IOAccelLegacyDisplayMachine`**;只覆盖 `init/start/stop/displayMode*`。而我们的
  `VIOAccelDisplayMachine` 继承的是 **legacy** 版。两条呈现路径:
  - 基类 machine → **transaction** 路径(`newDisplayPipeTransaction`/`validateTransaction`/
    `submitTransaction`/`isTransactionComplete`);
  - legacy machine → 追加 **flip** 路径(`setupScanout`/`submitScanoutFlipBuffer`/
    `submitFlipBuffer`)。
- **`AppleParavirtDisplayPipe` 只真正覆盖 `submitTransaction` + `validateTransaction` +
  `initFramebufferResource`**;`beginTransaction`/`signalTransactionComplete`/
  `newDisplayPipeTransaction`/`isTransactionComplete` 都是转调父类的 thunk。它**没有**
  `performTransaction` 覆盖 —— 它把拷贝放在 `submitTransaction` 里。
- 而 NVAccel(可用的第三方 x86 驱动)覆盖的恰恰是 **`performTransaction`**,没有
  `submitTransaction`。`kexts/NVRM/accel/iofam/IOAccelDisplayPipe.h` 里 **两个都是
  真实虚函数**(第 25、27 行),所以这**不是**"覆盖错了槽"——是同一 ABI 的两种实现风格。
  我们跟随 NVAccel 的 `performTransaction`,是合法且被验证过的选择。
- 结论:呈现路径的**方法名分歧已消解**。真正的未知量是 **legacy machine vs base
  machine** 的差别——legacy machine 会优先走 flip 路径。若实测 `performTransaction`
  从不被调用,再评估是否需补 legacy flip 那一组虚函数,或把 machine 退回基类。

## 7. `GetMTLTexture` 崩溃点 = 插件入口(2026-11-01,新)

用宿主 dyld 共享缓存反汇编 `_CoreDisplay_DisplaySurface_GetMTLTexture`
(`CoreDisplay + 0x6af5b`,`tmp/dis.py`)钉死了"过了闸之后的下一堵墙"到底要什么:

- 入参 `rdi` = DisplaySurface;它取 `[surface+0x80]` 的 vtable **slot +0x28** 得到
  `MetalDevice`,取 `[surface]`(即 `[surface+0]`)得到 **IOSurface**。
- 它构造一个 `MTLTextureDescriptor`,然后发一条**四参** objc 消息:
  **`[mtlDevice newTextureWithDescriptor:descriptor iosurface:iosurface plane:0]`**
  (调用点 `CoreDisplay+0x6b0f5`,`r8=0` 即 plane 0)。
- 返回 NULL 时,它拼串
  `"Failed to create MTLTexture on MTLDevice %@ with descriptor %@ and IOSurface creation properties %@"`
  然后 abort —— 这正是实验 A 看到的 SIGABRT。

**这正好是我们的插件已经实现的入口** `plugin/VMTLDevice.m:728`
`newTextureWithDescriptor:iosurface:plane:`。所以 4a 大概率**不需要新写接口**,只需确认
该路径对 CoreDisplay 传入的 descriptor(尤其 `MTLPixelFormat`、`usage` 含 ShaderWrite、
`storageMode`)与 IOSurface(非零 plane、BGRA)能成功返回非 nil。若它返回 nil,原因就在
`vmtl_surface_image_create`/`vmtl_pixfmt` 的取舍里,而不是缺方法。

## 8. IDA 伪代码钉死的精确条件(2026-11-14,新)

工具链:`tmp/dsc2macho.py`(从宿主 dyld cache 抠出 CoreDisplay 为独立 Mach-O)→
`tmp/dscfixup.py`(解 chained rebase,7766 个指针,selector/cfstring 全部可解析)→

**① `UseIOPresentment` 的完整判断**(`_CoreDisplay_UseIOPresentment` = 0x7ff801e007e9,
主体 `sub_7FF801DFCEF2`,`tmp/p43-useiop.c`):

```
return useIOP != 0 && gpuVendors != 0 && (gpuVendors & mask) == gpuVendors;
// mask 由 useIOP_onNVIDIA/onAMD/onAPV/onIG 组成:0x2 | 0x8 | 0x4 | 0x10
// 不匹配时还会把 useIOP 清 0(所以 poke 之后要一次成功)
```

**② `GetMTLTexture` 的真实主体是 `sub_7FF801E5BF70`**(export 0x7ff801e5bf5b 只是
thunk,对它做 xref 一无所获;对主体做 xref 才拿到 `RunFullDisplayPipe`)。全文
`tmp/p43-getmtltex.c`,两条分支都已确认 selector:

| 分支 | 调用 | 失败后果 |
|---|---|---|
| `*surface != 0`(有 IOSurfaceRef) | `newTextureWithDescriptor:iosurface:plane:`,plane=0,`setUsage:5`(ShaderRead\|RenderTarget,**不含** ShaderWrite) | 先打一条**含 descriptor 与 IOSurface creation properties 的完整日志**,然后 `if (![mtlDevice isRemovable]) abort();` |
| `*surface == 0`(IOAccel surface) | `newTextureWithSurface:surfaceID buffer:bufferIndex` | 只记日志,返回 nil,**不 abort** |

特殊像素格式 `'2vuy'`(846624121)/ `'2vuf'`(846624102)走 `pixelFormat=80`
(BGRA8Unorm)且宽度减半;其余格式经辅助函数转换。texture 的 label 分别是
`com.apple.CoreDisplay.iosurface` / `com.apple.CoreDisplay.ioaccelsurface`。

**③ 上游是 `CoreDisplay::DisplayPipe::RunFullDisplayPipe`**(`sub_7FF801EB0FD2`,
约 3200 行伪代码,`tmp/p43-present-chain.c`)。它是纯 Metal 合成:建 command buffer、
取 display surface 的 MTLTexture、准备 gamma LUT texture 与 render pipeline。**其中没有
任何 IOConnectCall** —— 也就是说把帧交给硬件不在这个函数里,而在 IOAccelerator 的
display machine 一侧。`GetMTLTexture` 返回 nil 时它**不崩**:清一层黑、重建
DisplaySurface、置重试标志后正常收尾。

**④ 由此得到的实现清单(本轮已落地)**:

- 实验 A 的 SIGABRT 不是"缺 `newTextureWithDescriptor:iosurface:plane:`",而是
  **texture 创建失败 + 设备回答 `isRemovable == NO`**。基类默认 NO,于是 abort,
  而那条最想要的诊断日志(descriptor + IOSurface properties)根本没机会被读到。
  → `plugin/VMTLDevice.m` 新增 `- (BOOL)isRemovable { return YES; }`:半虚拟化 GPU
  没有不可失去的固定显示,回答 YES 既符合硬件,又把致命 abort 变成 CoreDisplay
  的可读日志 + 重试。
- 新增 `newTextureWithSurface:buffer:`:IOAccelerator 的 surface 由 IOSurface 创建并沿用
  IOSurface ID,所以 `IOSurfaceLookup(surfaceID)` 后复用 IOSurface 路径;查不到或不支持的
  格式返回 nil(CoreDisplay 只记日志),并自己打日志,避免"静默黑屏"。

**⑤ 修正一条旧结论**:11-01 记的"caps 在 WS 启动前发布也被证伪"说过头了 —— 当时
`useIOP=0`,WindowServer 本来就不会进 IOP presentment,那次实验**不能**用来否定
display-pipe 路线。

## 9. 真实呈现已打通并通过冷启动验收(2026-11-14)

本节是当前状态,优先于上面的历史“空壳/0 次调用”描述。当前验收使用 macOS 15.8.1、
`tmp/p43-run.qcow2` 系统盘 overlay 和 `tmp/oc15-dev.qcow2`;QEMU 显卡为
`virtio-gpu-gl-pci,blob=on,hostmem=4G,venus=on`。所有改动尚未 commit,未 push。

### 9.1 从 family 初始化到 scanout 的完整实现

- **唯一 display pipe 绑定真实 framebuffer。** `VIOFBClaim` 阻止父 PCI nub 上通用的
  `IONDRVFramebuffer` 抢走 pipe;`debug.vioiop_gate` 现在显示
  `fb=VirtIOAppleParavirtFB`,且该对象与 `vioFramebufferService()` 返回的是同一实例。
- **scanout ABI 已按 IDA 伪代码修正。** `initScanoutResource()` 的返回类型是
  `IOAccelMemory *`,不是 `bool`。旧声明返回 `TRUE` 会让 family 把地址 `0x1` 当对象写入并
  panic。每个 framebuffer/scanout resource 创建独立 memory,由 family 的
  `destroy_*_resource()` 释放;不能跨 mode change 缓存裸指针。
  证据:`tmp/p43-scanout-memory-lifetime.c`;实现:`kexts/VirtIOGPU/VirtIOAccel.cpp:364-368,458-495`。
- **真正入口是 `submitTransaction()`。** AppleParavirt 覆盖它,NVAccel 则覆盖
  `performTransaction()`;本实现让前者转调后者,因此两种 family 路径最终都执行同一拷贝。
  `transaction_end()` 负责 prepare/build barrier,实际 submit 在 workloop 的
  `transaction_queue_gated()` 中经 vtable `+2232` 调用,不是 selector 8 直接同步调用。
  证据:`tmp/p43-family-transaction.c`;实现:`VirtIOAccel.cpp:502-558`。
- **每次事务完成真实呈现。** 从 plane 0 取得合成器 `IOSurface`,校验 BGRA、几何尺寸和
  pitch,prepare/map 源内存,按行复制到线性 scanout,再调用 `vioGPU_flushFrame()` 发
  `RESOURCE_TRANSFER_TO_HOST_2D + RESOURCE_FLUSH`。源 map 有 4 个复用 slot,析构时释放。
  拷贝同步完成,因此 `isTransactionComplete()` 可以立即返回 true。
- **原先三个 NotReady gate 已全部满足:** accelerator `+0xc78` bit 1 = 1,pipe `+0x282` = 0,
  pipe `+0x298` = 1。对应 framebuffer resource 初始化也完成(`fbinit=3/3`),resource 的
  memory 指针非空。

### 9.2 启动自动化:OpenCore boot-args 与 AGDC 竞态

  `PE_parse_boot_argn("debug.vioscanout", ...)` 和
  `PE_parse_boot_argn("debug.vioaccltypes", ...)`,同时提前设置 family 创建 scanout memory
